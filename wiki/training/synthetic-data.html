Synthetic Data / Procedural Synthesis

Synthetic Dataは、実データをそのまま増やすのではなく、既知の素材・simulation・生成モデル・規則から新しい学習sampleを作る戦略です。

Kaggleでは特に、label付き実データが少ない場合や、TrainとTestで見え方・配置・生成過程が違う場合に使われます。重要なのは「大量に作ること」ではなく、Testで起きる変化を生成規則へ入れることです。

仕組み

最も理解しづらい点は、Synthetic Dataが単なるData Augmentationではなく、「どの分布から学習sampleを出すか」を設計することです。

Real source
label付き素材
単体・clean・限定条件
＋
Generation rules
配置 / 姿勢 / scale / noise / compression
Testで起きる変化をモデル化
＝
Synthetic target-like data
labelを自動生成できる
Train/Test gapを縮める

模式図。生成規則はCompetitionごとに異なり、実測scoreを表す図ではありません。

たとえば単体CTしかlabelがなく、Testが多数の物体が詰まった3D volumeなら、単体volumeを回転・scale変換して複数配置すれば、位置とclassのground truthを構築時点で知ることができます。逆にTestに存在しないartifactを大量生成すると、modelはそのsynthetic artifactを覚えて悪化します。

使い分け

手法何を変えるか向く状況主なリスク

Kaggleでの実例

Forams2026 — 1位

Trainは「1 specimen / volume」、Testは約30個のshellが詰まったcolumnで、強いdomain gapがありました。1位解法は提供された単体CTからpacked columnをprocedural synthesisし、全モデルをsynthetic packed dataだけで学習しました。per-axis scale、3D rotation、flip、intensity scaling等も加えています（1st Place Solution Write-up）。Evidence: B — 1位本人の最終解法採用で、domain gapを閉じる中心戦略として明示されています。

UltraMNIST Classification Challenge — 1位

1位解法はCompetition dataに似たsynthetic imageを生成し、小型YOLOでobjectを検出した後、synthetic cropで学習した高精度classifierで再分類しました（1st Place Solution）。Evidence: B — synthetic generationが最終pipelineの明示的な構成要素です。

LLM - Detect AI Generated Text — 1位

1位チームはhidden testの生成essay仕様が不明なため、size・diversity・complexityを広げたgenerated essay群を段階的に構築しました。writeupではdataset qualityが重要で、複数single modelが0.970+に達したと報告しています（Comprehensive 1st Place Write-Up）。Evidence: B — 数値はdataset単独ablationではないため効果量とは扱いません。

DLMMDD Synthetic Image Attribution — 2位

Trainがclean、TestにはJPEG / WebP / crop / resize / rotation / blur等のpost-processingが入るdistribution mismatchに対し、2位解法はTest-time operationをtraining中にsimulationしました。最終scoreはPublic 0.9980 / Private 0.9973で、さらにsimulationしにくいartifactにはpseudo-labelingを併用しています（2nd Place Solution）。Evidence: B — 最終解法採用と有効性の明示はありますが、operation simulation単独の差は本文で確認できる範囲では分離されていません。

注意点

  • Generator artifactを学習しない: syntheticとrealを簡単に識別できる癖があると、本来のtargetではなく生成器を分類します。
  • Validationもtarget conditionへ寄せる: synthetic validationだけが高くてもreal Testへのtransferは保証されません。可能ならreal holdout、public/privateの安定性、複数生成条件で確認します。
  • 「variationを増やす」と「分布を壊す」は別: 現実に起こらないscale・noise・配置を増やすほど良いわけではありません。
  • 元データ由来のleakageを確認する: 同じsource objectから作った派生sampleがTrain/Validationへ跨る場合、source単位でsplitしないと過大評価になります。
  • 生成コストも制約: 高品質simulationやLLM生成は時間・GPU/API costが大きいため、追加data量ではなくcoverageを基準にします。

Quick Reference

使う

label不足または明確なdomain gapがあり、その差を生成規則として説明できる。

確認する

realism、coverage、source単位split、realに近いvalidation、generator artifact。

避ける

「dataが増えるから」という理由だけで、Testにない変化を無制限に生成する。
