Threshold Optimization

Threshold Optimization（閾値最適化）は、モデルが出したscore / probabilityを0・1やmaskへ変換するときの境界値を、Validation予測から選ぶ方法です。

F1、Dice、Precision、Recallのようにhard predictionで決まるMetricでは、同じモデルでもthresholdだけでscoreが変わります。0.5は初期値であって、常に最適な値ではありません。

ただしthresholdもhyperparameterです。TestやPublic LBを見て決めず、原則としてOOF（Out-of-Fold）prediction上で選び、fold間で安定しているかまで確認します。

仕組み

二値分類では、予測score p がthreshold t 以上ならpositive、それ未満ならnegativeにします。thresholdを下げるとpositive判定が増え、一般にRecallは上がりやすくPrecisionは下がりやすくなります。逆にthresholdを上げるとpositive判定が減ります。

Probability Calibrationとは別物

Threshold Optimizationは「どこで0/1へ切るか」を選びます。Probability Calibrationは「0.8という予測が本当に約80%の頻度で起きるようscoreの意味を整える」処理です。thresholdを変えてもprobability自体は校正されません。

OOFでの決め方

  1. 各foldのValidation predictionを保存してOOF predictionを作る。
  2. 公式Metricをローカルで再現する。
  3. threshold候補をOOF全体でsweepし、Metric curveを見る。
  4. OOF最良値だけでなく、foldごとの最良thresholdとscore低下幅を確認する。
  5. 鋭い1点だけが勝つなら過適合を疑い、広いplateau内の安定した値を優先する。
  6. 選んだthresholdを固定し、Test predictionへ一度だけ適用する。

scikit-learnのdecision threshold guideでも、threshold tuningは独立したValidation / cross-validationで行う設計が示されています。学習に使った同じpredictionへthresholdをfitして、そのscoreをそのまま性能として扱わないことが重要です。

Kaggleでの実例

SPR 2026 Mammography Report Classification — 3rd place

2026年のSPR Mammography Report Classification 3位解法は、multi-head TF-IDF + LightGBMのclass別thresholdをOOFでgrid searchし、baseline threshold比でOOF macro-F1 +0.01867、Private score 0.85431と報告しています（3rd Place Solution）。定量ablationがあるためEvidence Aです。

MABe Mouse Behavior Detection — 3rd place

MABe 3位解法では、blended probabilityに対してlab × actionごとのthresholdをOOF predictionでgrid searchしています。複数actionが同一frameでpositiveになった場合は probability / threshold の比が最大のactionを残す設計です（3rd place solution）。採用は確認できますがthreshold単独のablation値は示されていないためEvidence Bとして扱います。

Quora Insincere Questions Classification — 1st place

1位チームはfoldごとにoptimal thresholdが大きく変動する問題を確認し、CV上でF1のoptimal値からのdeviationが小さい安定したfixed thresholdを探しています。またprobability平均よりrank平均の方がthresholdを安定させたと報告しています（1st place solution）。「OOF最大の1点」ではなくfold間安定性を見る実例です。

Vesuvius Challenge - Ink Detection — 1st place

1位解法はAUC、Precision、Recall、F0.5をthreshold sweepで継続監視し、modelごとにoptimal thresholdが広く異なることを確認しています。ensemble後はthresholdが0.5付近へ安定したと報告しており、最後の0.55 submissionはPublicでは悪化した一方Privateではわずかに高かったと記しています（1st place solution）。Public LBだけでthresholdを決める危険性も示す例です。

注意点

Test / Public LBでthresholdを選ぶ

submissionを何度も投げてthresholdを選ぶと、Public subsetへfitしたhyperparameterになります。OOFで決め、Public LBは異常検知程度に使います。

OOF全体の最大値だけを見る

threshold curveが尖っている、foldごとの最良thresholdが大きく違う場合、Testで再現しにくい可能性があります。最良scoreだけでなくplateau幅とfold分散を確認します。

class別thresholdを増やしすぎる

100 classなら100個の自由parameterを持つことになります。rare classほどValidation sampleが少なく、極端なthresholdへ寄りやすいため、global threshold、group共有、正則化された探索も比較します。

Metricがthresholdを必要としない

ROC-AUCはranking、LogLossやBrier Scoreはprobabilityを直接評価します。提出形式が連続値ならhard threshold化は通常不要です。CompetitionのEvaluationとsubmission formatを先に確認します。

distribution shift

OOFとTestでpositive rateやscore分布が変わるとoptimal thresholdも動きます。threshold調整でshiftそのものを解決しようとせず、Adversarial Validationやsplit設計も確認します。

Quick Reference

  • F1 / Dice等のhard prediction Metricならthresholdを実験対象にする。
  • thresholdはOOFで決める。Train predictionやPublic LBでfitしない。
  • best scoreだけでなくfold間のthreshold分散とplateau幅を見る。
  • class別thresholdは自由度が増えるのでablationする。
  • ROC-AUC / LogLoss / Brierなど連続score Metricではthresholdの要否を再確認する。
